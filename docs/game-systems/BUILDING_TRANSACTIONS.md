# Server Building Transactions

> Status: server-authoritative place/move endpoint is implemented and bootstrapped. Studio/remote integration verification is pending.

## Remote contract

The server creates `ReplicatedStorage/Remotes/PlaceBuilding` as a RemoteFunction. Clients invoke it with:

```lua
{
    requestId = "client-generated-unique-id",
    catalogId = "main_house",
    x = 2, -- integer minimum X grid cell
    z = 3, -- integer minimum Z grid cell
    rotation = 90,
    movingInstanceId = nil, -- set to an owned instance ID to move
}
```

The server derives the player identity from the invoking Player, reads the active server profile, resolves dimensions/unlocks from BuildingCatalog, and validates with PlacementValidator. Client-provided prices, dimensions, previous coordinates, and ownership are never accepted.

Successful responses contain `ok`, `code`, `instanceId`, `catalogId`, `x`, `z`, and `rotation`. Failures return `ok = false` and a stable error code. Repeated request IDs return the cached result for that player (bounded to 64 recent IDs) and do not consume another rate-limit token. The remote also uses a per-player token bucket: burst capacity 12 requests, refilling at 4 requests/second. Excess requests fail with `RATE_LIMITED`; bucket state is removed when the player leaves.

## Transaction behavior

1. Validate request shape and idempotency key.
2. Resolve the active profile and validate ownership, unlock, rotation, bounds, overlap, and move target.
3. Build the new record on the server; new instance IDs are generated by HttpService.
4. Synchronize the server-owned Model from `ServerStorage/BuildingModels/<catalogId>`.
5. Update the profile record and mark the session dirty/revisioned.
6. Return success only after the server-side model and profile mutation succeed.

If model synchronization fails, the profile is rolled back and no success is returned. If the session becomes non-writable before dirty marking, the profile and world model are rolled back. This milestone does not charge resources: costs and economy values are not approved yet.

## Model requirements

Each building template must be a Model in `ServerStorage/BuildingModels`, named by stable catalog ID. Its pivot must be authored at the ground-level origin/center convention documented in `ISLAND_WORLD_RENDERING.md`. The server tags spawned models with `BuildingInstanceId` to support safe replacement during moves.

## Client usage

A future client controller can call:

```lua
local remote = game:GetService("ReplicatedStorage")
    :WaitForChild("Remotes")
    :WaitForChild("PlaceBuilding")

local result = remote:InvokeServer({
    requestId = game:GetService("HttpService"):GenerateGUID(false),
    catalogId = "main_house",
    x = 2,
    z = 2,
    rotation = 0,
})
```

The client must treat the response as authoritative. A preview is cosmetic only and must not locally commit the building.

## Verification checklist

- Run `PlacementValidatorTests.server.lua` in Studio.
- Configure Workspace grid attributes, spawn points, and a test Model named `main_house`.
- Invoke the RemoteFunction as a real player and verify valid placement updates the model and profile.
- Verify overlap, out-of-bounds, locked/unknown IDs, invalid rotations, and spoofed move targets are rejected.
- Repeat the same request ID and verify no duplicate model/profile record is created.
- Move a building and verify its old model is replaced, not duplicated.
- Remove/rename a template and verify the transaction fails without changing the saved profile.
- Rejoin and verify the accepted building is restored from DataStore.
